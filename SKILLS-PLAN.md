## Proposed skills

### 1. wiki-page-lifecycle
**Purpose:** Create, move, or retire a page without breaking links or deploys.
**Triggers when:** "add a page", "move X to Guides", "delete/rename a page", new section work, any structural change to docs/ or nav.
**Priority:** high
**Structure:** SKILL.md
**Content:**
- Two-step registration: create the file AND add it to `nav` in mkdocs.yml. A page outside `nav` is unreachable; Zensical does not validate nav entries.
- Slugs are load-bearing: zoompilot.ai deep-links wiki paths (notably `/features/...`). Every move or removal needs a 301 in `contrib/_redirects`, written twice — with and without trailing slash.
- Before any heading rename: grep all inbound `page.md#anchor` links across the repo. JS widgets (troubleshoot wizard, settings explorer, section cards) hardcode hrefs; reordering headings is safe, retitling is not.
- Update the section index card grid, frontmatter (`title:` matching the single H1, `reviewed:` stamp on content pages), then `.venv/bin/zensical build --strict` before push.
- Removed pages never just vanish: point the redirect at the nearest surviving page or the external canonical (docs.comma.ai) page, and repoint inbound links.

### 2. write-wiki-page
**Purpose:** Write user-facing content in the house register.
**Triggers when:** writing or rewording content on any user-facing page (everything outside `docs/technical/`).
**Priority:** high
**Structure:** SKILL.md
**Content:**
- Plain everyday words on user pages ("comes preconfigured", not dev-speak); `technical/` pages keep code terms and near-verbatim imports (keep the author's voice; change structure/links only).
- No boundary claims: describe what the system does, never what it does not. Futures live on the roadmap page only.
- Capability claims name the exact part ("Mazdas with a 2022-25 CX-5 EPS motor"), never a looser year range; car claims keep model-year form.
- Acronyms: spell out on first use; an "(ABBR)" parenthetical only pays off when the acronym recurs on the same page — target pages introduce their own acronyms. `docs/includes/abbreviations.md` stamps sitewide tooltips on every match of every page: grep all pages for the bare token before adding an entry.
- Safety pages keep comma's wording verbatim in the frozen sections (basis/fork-rules/Limitations); titles, formatting, and hrefs may change. State each fact once; short sentences, active voice.

### 3. site-sync
**Purpose:** Land releases and keep wiki and site data in step.
**Triggers when:** "a release landed", handling a "Wiki drift" issue, editing the supported-cars table, changelog work, anything touching generated files.
**Priority:** high
**Structure:** SKILL.md
**Content:**
- Release flow: transcribe zoompilot.ai release notes into the site repo's `src/data/changelog.js` → run `npm run sync:wiki` FROM the site repo → commit and push BOTH repos (wiki push auto-deploys).
- Four wiki files are generated (`docs/releases/changelog.md`, `docs/assets/steering-torque.svg`, `docs/assets/steering-torque-data.js`, `docs/technical/route-library.md`); hand edits get stomped or halt sync. On a guard halt, fix the source in the site repo, then `--force`. The hand-written "## Upstream release notes" tail of the changelog is never touched by sync.
- The FIRST table of `docs/getting-started/supported-cars.md` flows wiki → site (site renders it from JSON); a table edit needs a sync run or the site copy lags.
- Drift watchdog: `.github/workflows/drift-check.yml` runs daily and opens/updates one "Wiki drift:" issue; clearing it means landing the release and/or refreshing the `docs/technical/` mirror from the zoompilot repo's `docs/zoompilot`.
- Runbook of record: `docs/reference/site-sync.md`. Known stale row there: it lists `assets/js/car-checker-data.js` as generated, but that file does not exist.

### 4. update-settings-page
**Purpose:** Refresh the settings page when upstream settings change.
**Triggers when:** release watch flags settings drift, "a new setting appeared", screenshot refresh, settings-page edits.
**Priority:** medium
**Structure:** SKILL.md
**Content:**
- `docs/assets/js/settings-data.js` is the single hand-edited source for the card view; on-device settings changes edit this file, not the page HTML.
- Page DOM contract per panel: H2 → `details.zp-collapse` with the figure pair → intro → mount div (`data-panel`). The explorer script walks siblings from the mount; never wrap or reorder them.
- Screenshots are simulator renders, not device photos: regeneration procedure in `docs/assets/settings/README.md` (run `contrib/capture-settings.py` from a zoompilot clone, `DEVICE=tici` for comma 3/3X, both device variants required).
- A new panel = two image files (mici strip + tici shot) + one figure pair + entries in settings-data.js.

### 5. deploy-wiki
**Purpose:** Ship changes and verify the deploy really happened.
**Triggers when:** deploy questions, "the push didn't publish", rollback, manual deploy, Cloudflare Pages work.
**Priority:** medium
**Structure:** SKILL.md
**Content:**
- Push to main auto-deploys via `.github/workflows/cloudflare-pages.yml`. Footgun: missing Cloudflare secrets make CI skip the deploy with only a notice — the run looks green.
- The manual fallback `npm run deploy` does NOT copy `contrib/_redirects`; only CI copies both `_headers` and `_redirects`. A manual deploy loses all redirects.
- Always `.venv/bin/zensical build --strict` first; broken internal links fail the build. Bare `zensical` is not on PATH; output always goes to `site/` (no `--site-dir` flag).
- Rollback: `npx wrangler pages deployment list --project-name zoompilot-wiki` then `npx wrangler pages deployment rollback ...`. Custom domain work is declined — do not plan DNS or domain changes.
